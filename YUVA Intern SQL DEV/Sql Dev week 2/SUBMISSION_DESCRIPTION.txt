This Week 2 report presents a detailed ETL planning design for a hypothetical online retail environment and reuses the PostgreSQL relational model developed in Week 1 as the target database. It identifies realistic source systems for customer registrations, product catalogues, orders, order items, warehouse inventory, supplier records, payment events, and shipment updates. The proposed pipeline extracts data from CSV/XLSX files, REST APIs, and relational exports, assigns a batch identifier, and stores the original values in raw staging tables before applying transformations. The transformation strategy includes trimming whitespace, standardizing email and status values, parsing dates with explicit formats, converting numeric fields safely, handling optional NULL values, identifying duplicates using normalized business keys, and validating required fields. It also defines retail-specific rules: product prices cannot be negative, order quantities must be positive, inventory cannot fall below zero unless backorders are allowed, orders must reference existing customers, and order lines must resolve to valid products. Invalid records are routed to a reject log with their source key and rejection reason rather than being silently discarded. The report compares full, incremental, and upsert loading, explains parent-before-child loading order, and recommends stable source-to-target key mapping because PostgreSQL identity values may differ from source IDs. Concrete sample CSV files contain 30 illustrative records with deliberately introduced quality issues, allowing the validation logic to be reviewed against worked examples. SQL examples cover staging, data-quality checks, standardization, conflict handling, and incremental watermarks. The design additionally addresses batch reconciliation, transaction safety, retry handling, indexing, bulk loading with COPY, monitoring, least-privilege access, and protection of payment and customer data. The document is a planning deliverable; actual execution results should be recorded only after the scripts are tested against the installed Week 1 database.

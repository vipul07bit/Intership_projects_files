This Week 5 report presents an integrated SQL automation strategy for the virtual retail database developed during the earlier weeks of the SQL Developer internship. It builds on the retail schema containing customers, products, warehouses, inventory, orders and order_items, and documents the assumptions required to apply the scripts safely to an existing PostgreSQL database. The implementation includes a transaction-safe stored procedure for processing a sale, an inventory trigger for recording stock movements and creating or resolving low-stock alerts, and scheduled procedures for capturing daily inventory snapshots and archiving older sales records. An automation log records process status, completion time, row counts and error details.

The sale procedure validates the customer, active product, quantity and warehouse stock. It locks the relevant inventory row before decrementing stock, which helps prevent overselling when concurrent checkout requests target the same product and warehouse. The trigger centralizes low-stock business rules and maintains at most one open alert for each product/warehouse pair. The archive workflow is deliberately non-destructive: eligible orders and their line items are copied to archive tables, while source records are retained until a formal retention and recovery policy is approved.

The report also defines inventory turnover and stock cover days using a consistent 30-day period. It explains the formulas, business interpretation, data requirements and limitations, including the need for daily inventory snapshots and reliable unit-cost data. Supporting charts are included as clearly labeled synthetic illustrations, not as measured production results. The package contains ordered SQL scripts, deterministic demonstration data, automated SQL assertions, optional pg_cron scheduling instructions, execution scripts for Bash and PowerShell, architecture diagrams and a test evidence template.

The scripts are designed to be run with PostgreSQL and psql through a single execution harness. Actual database execution evidence, runtime measurements, query plans and screenshots should be captured from the internship database before final submission; the generated package does not claim that a live database was available during preparation.
